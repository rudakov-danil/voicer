# Data Pipeline — путь данных от записи до дашборда

Это центральный процесс платформы. Здесь описывается, что именно происходит с данными на каждом шаге — от момента, когда продавец начинает разговор, до момента, когда руководитель видит аналитику на дашборде.

---

## Обзор пайплайна

```
[Разговор в торговом зале]
        ↓
[Аудиобейдж записывает аудио весь день на SD-карту]
        ↓
[Бейдж ставится на зарядку в dok-станцию]
        ↓
 Шаг 1: Загрузка записей         — recorder-service
        ↓
 Шаг 2: Склейка и сегментация    — recorder-service / transcription-service
        ↓
 Шаг 3: Транскрибация            — transcription-service
        ↓
 Шаг 4: Идентификация ролей      — transcription-service (LLM)
        ↓
 Шаг 5: AI-анализ                — analytics-engine
        ↓
 Шаг 6: Попадание в дашборд      — dashboard-service
        ↓
[Руководитель видит аналитику]
```

Весь пайплайн асинхронный. Каждый шаг не ждёт ответа от следующего — он публикует задание в очередь и освобождается для обработки новых данных.

---

## Шаг 0 — Аудиобейдж: запись в течение дня

Продавец носит небольшое устройство-бейдж, которое:
- **Записывает непрерывно** весь рабочий день через встроенный микрофон
- Запись ведётся **не одним цельным файлом**, а **множеством коротких аудиочанков** на SD-карту
- Каждый чанк содержит временну́ю метку начала и конца записи (UTC)
- Устройство идентифицируется по уникальному `device_id`, зашитому в прошивку

**Технические требования к аудио:**
- Формат: WAV (предпочтительно), MP3, OGG
- Максимальный размер одного чанка: ~100 МБ
- Частота дискретизации: 16 кГц и выше (необходимо для качественной транскрибации)

**Когда бейдж ставится на зарядку в dok-станцию:**
- Dok-станция подключена к Wi-Fi
- Все накопленные чанки с SD-карты автоматически загружаются на сервер
- Каждый чанк отправляется с `device_id` и временными метками

---

## Шаг 1 — Загрузка записей (recorder-service)

**Что происходит:**

1. Dok-станция отправляет `POST /api/v1/recordings/upload` — multipart-запрос с аудиочанком и метаданными

2. **Валидация:**
   - Файл не пустой и имеет поддерживаемый формат
   - `device_id` зарегистрирован в системе и привязан к продавцу и организации
   - Нет дубля — вычисляется хеш файла, проверяется уникальность

3. **Сохранение аудиочанка в MinIO:**
   - Файл сохраняется по пути: `voiceiq-recordings/{organization_id}/{store_id}/{seller_id}/{date}/{uuid}.wav`

4. **Запись метаданных в PostgreSQL:**
   - Создаётся запись в таблице `recordings` со статусом `uploaded`
   - Фиксируются: продавец, магазин, организация, устройство, временны́е метки чанка, размер файла

5. **Публикация в очередь:**
   - После загрузки **всех** чанков dok-станция отправляет финальный сигнал: `POST /api/v1/recordings/upload-complete` с `{ device_id, session_date }`
   - Только после этого сигнала recorder-service публикует задание на склейку в `queue.stitch`
   - Payload: `{ device_id, session_date, chunk_ids[] }`
   - Это гарантирует, что склейка не начнётся раньше, чем все чанки дойдут до сервера

---

## Шаг 2 — Склейка чанков (recorder-service)

После загрузки всех чанков за день сервис склеивает их в единый суточный файл.

1. Чанки сортируются по временным меткам начала
2. Объединяются в один непрерывный аудиофайл (полная запись рабочего дня продавца)
3. Итоговый файл сохраняется в MinIO: `voiceiq-recordings/{org_id}/{store_id}/{seller_id}/{date}/full_day.wav`

**Публикация:**
- Публикуется задание в `queue.transcribe_full`
- Payload: `{ device_id, seller_id, store_id, organization_id, audio_path, session_date }`
- Сопоставление `device_id` → `seller_id` выполняется на шаге 1 при загрузке чанков через admin-service

---

## Шаг 3 — Транскрибация суточного файла + сегментация (transcription-service)

**Что происходит:**

Воркер-консьюмер забирает задание из `queue.transcribe_full` и начинает обработку.

1. **Загрузка суточного файла:** из MinIO загружается `full_day.wav`

2. **Отправка в Whisper (self-hosted):**
   - Whisper транскрибирует весь суточный файл в текст
   - Возвращает: текст с таймкодами для каждого слова/фразы
   - Whisper **не определяет роли и не делит на разговоры** — только переводит речь в текст

3. **Постобработка текста:**
   - Расстановка пунктуации
   - Нормализация чисел (например, "тридцать пять тысяч" → "35 000")
   - Удаление слов-паразитов — опционально, настраивается

4. **Сегментация разговоров через LLM:**
   - LLM получает полный транскрипт суточного файла с таймкодами
   - Определяет границы отдельных разговоров **по контексту**: приветствие, прощание, смена темы
   - Возвращает список разговоров: `[{ start_time, end_time }, ...]`

5. **Нарезка аудио:**
   - Для каждого найденного разговора аудио **физически вырезается** из `full_day.wav` и сохраняется в MinIO: `audio/{org_id}/{store_id}/{seller_id}/{date}/{uuid}.wav`
   - `full_day.wav` удаляется после нарезки
   - Для каждого разговора создаётся запись в `recorder.recordings` со статусом `segmented`

6. **Сохранение транскриптов в PostgreSQL:**
   - Для каждого разговора: полный текст сегмента, таймкоды реплик (роли пока не определены)
   - Статус обновляется до `transcribed`

7. **Публикация следующего задания:**
   - Для каждого разговора в `queue.diarize`: `{ recording_id, transcript_id, seller_id, store_id, organization_id }`

**Целевое время:** транскрибация суточного файла — до 2× его длительности.

---

## Шаг 4 — Идентификация ролей (transcription-service)

Whisper возвращает текст без разделения на спикеров. Определение ролей выполняется отдельным LLM-запросом для каждого разговора.

**Что происходит:**

1. Загружается транскрипт разговора из шага 3 — текст с таймкодами реплик
2. По `seller_id` из базы берётся имя продавца (`full_name`) — оно передаётся в промпт как контекст
3. LLM-запрос:

```
Вот транскрипт разговора в магазине.
Продавец: Алексей Иванов.
Раздели разговор на реплики и определи для каждой: кто говорит — продавец или клиент.

Транскрипт:
{full_text_with_timecodes}

Верни JSON: список объектов { text, start_time, end_time, speaker: "seller" | "client" }
```

4. Результат сохраняется в `transcript_segments` — каждый сегмент получает поле `speaker` (`seller` / `client`)
5. Статус записи обновляется до `diarized`
6. Публикуется задание в `queue.analyze`

---

## Шаг 5 — AI-анализ (analytics-engine)

Воркер забирает задание из `queue.analyze`. Для каждого разговора выполняется **один большой LLM-запрос**, который охватывает все 4 вида анализа одновременно.

Подробное описание — в [ai-analysis.md](./ai-analysis.md).

**Три этапа анализа:**
1. **Скрининг контекстных скриптов** — LLM определяет, какие контекстные скрипты применимы к данному разговору
2. **Скоринг по применимым скриптам** — оценка выполнения каждого этапа каждого скрипта (0–100)
3. **Общий анализ** — классификация возражений, определение исхода, тема, тональность

После анализа:
- Результаты сохраняются в схему `analytics` в PostgreSQL
- Статус записи обновляется до `analyzed`
- В `queue.cache.invalidate` публикуется событие, чтобы dashboard-service обновил кэш

**Целевое время:** не более 30 секунд на один разговор.

---

## Шаг 6 — Попадание в дашборд (dashboard-service)

Dashboard-service — это BFF (Backend for Frontend). Он не хранит собственных данных, а агрегирует их из PostgreSQL и кэширует в Redis.

**Что происходит при инвалидации кэша:**

1. analytics-engine публикует `{ store_id, organization_id }` в `queue.cache.invalidate`
2. Dashboard-service получает событие и удаляет устаревшие ключи из Redis
3. При следующем запросе с фронтенда — данные заново агрегируются из БД и кэшируются

**Кэширование:**
- Ключ кэша: `dashboard:{organization_id}:{store_id}:{period}:{endpoint}`
- TTL для `/overview`: 5 минут
- TTL для `/team/leaderboard`: 15 минут

## Обработка ошибок

На каждом шаге пайплайна предусмотрена защита от сбоев.

| Ситуация | Поведение |
|----------|-----------|
| Ошибка при загрузке чанка | Dok-станция получает ошибку и повторяет попытку |
| Ошибка при транскрибации | 3 автоматические попытки, затем задание → DLQ, статус → `error` |
| Ошибка при идентификации ролей | 3 автоматические попытки, затем → DLQ |
| Ошибка при AI-анализе | 3 автоматические попытки, затем → DLQ |
| Задание в DLQ | Мониторится в Grafana, алерт команде разработки |
| Ручной перезапуск транскрибации | `POST /api/v1/transcripts/retry/{recording_id}` |
| Ручной перезапуск AI-анализа | `POST /api/v1/analytics/reanalyze/{id}` |

**Dead Letter Queue (DLQ)** — специальная очередь для задач, которые не удалось обработать после 3 попыток. Задания в DLQ не теряются — они ждут ручного вмешательства.

---

## Статусы записи

Запись проходит через следующие статусы:

```
uploaded → transcribing → transcribed → diarized → analyzing → analyzed
                                                                    ↓
                                                                 (error)
```

| Статус | Когда устанавливается |
|--------|----------------------|
| `uploaded` | Аудиочанк успешно принят и сохранён в MinIO |
| `transcribing` | Задание на транскрибацию отправлено в очередь |
| `transcribed` | Whisper завершил транскрибацию, получен транскрипт |
| `segmented` | LLM определил границы разговоров, аудио нарезано на отдельные файлы |
| `diarized` | LLM определил роли спикеров в каждом разговоре |
| `analyzed` | AI-анализ завершён, данные в дашборде |
| `error` | Ошибка на одном из шагов (подробности в логах) |

---

## Время обработки

| Этап | Целевое время |
|------|--------------|
| Загрузка чанков | Секунды (зависит от размера и Wi-Fi) |
| Склейка и VAD-сегментация | < 1 минуты на суточный файл |
| Транскрибация (Whisper) | До 2× от длительности разговора |
| Идентификация ролей (LLM) | 5–15 секунд |
| AI-анализ | До 30 секунд |
| Попадание в кэш дашборда | Секунды после завершения анализа |
| **Итого (5-минутный разговор)** | **~15–25 минут** |

Бо́льшая часть времени — транскрибация через Whisper. При большой нагрузке можно масштабировать воркеры горизонтально.
