# Архитектура системы

## Принципы построения

VoiceIQ построен по микросервисной архитектуре. Каждый сервис — это отдельный Docker-контейнер, который отвечает за строго определённую доменную область и не имеет прямого доступа к данным других сервисов.

**Почему микросервисы:**
- Независимое масштабирование — воркеры транскрибации и анализа можно масштабировать отдельно, не затрагивая остальные сервисы
- Изолированные сбои — если упал один сервис, остальные продолжают работать
- Параллельная разработка — разные разработчики работают над разными сервисами без конфликтов

**Асинхронная обработка:** тяжёлые задачи (транскрибация аудио, AI-анализ) не выполняются синхронно в рамках HTTP-запроса. Они попадают в очередь RabbitMQ и обрабатываются воркерами в фоне. Это позволяет системе не блокироваться и принимать новые записи, пока старые ещё обрабатываются.

**API-first:** frontend никогда не обращается напрямую к конкретным сервисам. Все запросы идут через API Gateway, который маршрутизирует их к нужному сервису. Сервисы между собой тоже общаются через REST API, а не через прямые вызовы функций или общую память.

**Мультитенантность:** каждая компания-клиент — это изолированная организация. Данные разных организаций никогда не смешиваются. Изоляция обеспечивается на уровне `organization_id` во всех запросах к базе данных.

## Технологический стек

| Компонент | Технология | Зачем |
|-----------|------------|-------|
| API Gateway | Traefik / Nginx | Единая точка входа, маршрутизация, rate limiting, SSL |
| Backend-сервисы | Python + FastAPI | Быстрая разработка, нативная асинхронность, интеграция с ML |
| Фронтенд | React + TypeScript + Vite | Компонентный подход, типизация, быстрая сборка |
| UI-библиотеки | Recharts, shadcn/ui, TanStack Table | Графики, UI-компоненты, таблицы с фильтрацией |
| База данных | PostgreSQL 16 | Надёжная реляционная БД с поддержкой JSON |
| Кэш / сессии | Redis | Кэширование агрегаций, JWT blacklist |
| Очередь сообщений | RabbitMQ | Асинхронные задачи между сервисами |
| Хранилище аудио | MinIO (S3-совместимый) | Объектное хранилище для аудиофайлов |
| STT-движок | **Whisper (self-hosted, отдельный GPU-сервер)** | Транскрибация речи в текст |
| LLM для анализа | **Локальные модели через Ollama (MVP) → vLLM** | Скоринг скриптов, классификация возражений, диаризация |
| Контейнеризация | Docker + Docker Compose | Единообразное окружение |
| CI/CD | GitHub Actions | Автоматическая сборка, тесты, деплой |
| Мониторинг | Prometheus + Grafana | Метрики сервисов, алерты |
| Логирование | Loki / ELK | Централизованные логи |

> **STT:** используется только Whisper (self-hosted). Яндекс SpeechKit не используется — данные не передаются во внешние API при транскрибации.

> **LLM:** используются локальные языковые модели, запущенные на собственном GPU-сервере. MVP — Ollama (простой запуск, REST API). Продакшн — vLLM (выше производительность, поддерживает OpenAI-совместимый API). Данные не покидают инфраструктуру, соответствие 152-ФЗ.

## Инфраструктурные компоненты

### PostgreSQL — единая БД с логическим разделением

Одна PostgreSQL-инстанция обслуживает все сервисы, но данные разделены на логические схемы (schemas):
- `auth` — пользователи, токены, организации
- `admin_schema` — магазины, продавцы, устройства, назначения ропов
- `recorder` — записи
- `transcription` — транскрипты и сегменты
- `scripts` — шаблоны скриптов
- `analytics` — разговоры, скоринг, возражения

**Правило:** каждый сервис работает только со своей схемой. Данные из чужих схем он получает только через API соответствующего сервиса.

### RabbitMQ — очереди для async-задач

Основные очереди:
- `queue.stitch` — задания на склейку чанков
- `queue.transcribe_full` — задания на транскрибацию (recorder → transcription)
- `queue.diarize` — задания на идентификацию ролей (transcription → transcription)
- `queue.analyze` — задания на AI-анализ (transcription → analytics)
- `queue.cache.invalidate` — инвалидация кэша дашборда (analytics → dashboard)

При ошибке обработки: 3 повторные попытки, затем задание отправляется в Dead Letter Queue (DLQ). Состояние DLQ мониторится через Grafana.

### MinIO — объектное хранилище аудио

S3-совместимое хранилище для MVP. Для продакшена заменяется на Yandex Object Storage.

Структура путей: `voiceiq-recordings/{organization_id}/{store_id}/{seller_id}/{date}/{filename}.wav`

### Redis — кэш и сессии

- Кэширование тяжёлых агрегаций дашборда (TTL 5–15 минут)
- Хранение JWT blacklist (при logout токен попадает в Redis и не принимается до истечения)

### Whisper — self-hosted STT

Whisper запускается на **отдельном GPU-сервере** (не в основном docker-compose). Модель: `whisper-large-v3` для русской речи.
- Транскрибирует аудио в текст с таймкодами
- Не определяет спикеров — только переводит речь в текст
- Работает полностью локально, данные не передаются во внешние API
- `transcription-service` обращается к Whisper по HTTP (переменная окружения `WHISPER_SERVER_URL`)

### Ollama / vLLM — self-hosted LLM

LLM запускается на **отдельном GPU-сервере** (отдельном от Whisper).
- **MVP:** Ollama — простой запуск, стандартный REST API, поддерживает Llama, Mistral, Qwen и другие открытые модели
- **Продакшн:** vLLM — более высокая пропускная способность, OpenAI-совместимый API
- Все сервисы, использующие LLM (`transcription-service`, `analytics-engine`), обращаются к нему по HTTP (переменная окружения `LLM_SERVER_URL`)
- Стартовая модель: `qwen2.5:14b` (конфигурируется через `LLM_MODEL_NAME` env, меняется без правки кода)

## Схема взаимодействия сервисов

### Асинхронный поток (обработка записей)

```
Dok-станция (бейдж)
  → POST /upload (чанки) → recorder-service
      → сохранение чанков в MinIO
      → запись metadata в PostgreSQL
      → публикация в queue.stitch
          → recorder-service (воркер)
              → склейка чанков → суточный файл (full_day.wav)
              → публикация в queue.transcribe_full
                  → transcription-service (воркер)
                      → Whisper STT: транскрибация full_day.wav → текст с таймкодами
                      → LLM: сегментация по контексту → границы разговоров
                      → физическая нарезка аудио → отдельные WAV-файлы в MinIO
                      → full_day.wav удаляется
                      → сохранение в PostgreSQL
                      → публикация в queue.diarize
                          → transcription-service (воркер)
                              → LLM: определение ролей (с именем продавца)
                              → сохранение сегментов с ролями
                              → публикация в queue.analyze
                                  → analytics-engine (воркер)
                                      → запрос скрипта у scripts-service
                                      → LLM-запросы: скрининг скриптов + скоринг + возражения + исход
                                      → сохранение результатов в PostgreSQL
                                      → публикация в queue.cache.invalidate
                                          → dashboard-service инвалидирует кэш Redis
```

### Синхронные запросы (REST)

```
Frontend → API Gateway → auth-service          (вход, токен, профиль)
Frontend → API Gateway → dashboard-service     (дашборды, метрики)
Frontend → API Gateway → scripts-service       (CRUD скриптов)
Frontend → API Gateway → admin-service         (магазины, продавцы, устройства)
analytics-engine → scripts-service             (получить скрипты продавца для скоринга)
```

## Масштабирование

Для MVP запускается по одному экземпляру каждого сервиса, кроме воркеров:

- **transcription-worker**: 2–3 экземпляра для параллельной обработки записей
- **analytics-worker**: 2–3 экземпляра

При росте нагрузки (например, 100+ записей в час) количество воркеров увеличивается независимо от остальных сервисов. В продакшене оркестрация переходит с Docker Compose на Kubernetes (Yandex Cloud).
