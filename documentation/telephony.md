# Телефония — речевая аналитика звонков

Ответвление продукта для клиентов, продающих по телефону: контакт-центры, отделы продаж,
клиники, автодилеры и т.д. Включается на уровне организации: `org_type = telephony`
(Настройки → Организация). Меняет терминологию UI (Отдел/Оператор/Звонок) и открывает
телефонийные функции.

---

## Чем звонок отличается от записи с бейджа

Звонок — это уже готовый отдельный разговор с метаданными. Поэтому:
- **Не нужны** склейка чанков и LLM-сегментация суточного файла — звонок входит в пайплайн
  сразу на этапе транскрибации.
- **Стерео-записи АТС** (оператор и клиент в раздельных каналах) дают 100%-точную
  диаризацию по каналам — без LLM-запроса. Моно-записи идут по обычному пути
  (кластерная/LLM-диаризация).
- У записи появляются метаданные: направление, номер клиента, добавочный оператора,
  ID звонка в АТС.

## Как звонки попадают в систему

| Способ | Эндпоинт | Auth |
|--------|----------|------|
| Ручная загрузка звонка (UI «Загрузить звонок») | `POST /api/v1/recorder/telephony/calls` | JWT |
| Вебхук от АТС | `POST /api/v1/recorder/telephony/webhook/{token}` | токен организации |
| Простая загрузка аудио (как раньше, для тестов) | `POST /api/v1/recorder/upload` | JWT |
| Прямая загрузка транскрипта (для тестов, без аудио) | `POST /api/v1/transcription/upload-transcript` | JWT |

### Вебхук АТС

Настройки: Настройки → Телефония (URL вебхука, перевыпуск токена, отдел/оператор по
умолчанию, канал оператора в стерео). Формат запроса:

```json
{
  "external_call_id": "id-звонка-в-АТС",
  "direction": "inbound",
  "client_phone": "+79991234567",
  "operator_phone": "101",
  "recording_url": "https://pbx.example.com/records/abc.mp3",
  "started_at": "2026-06-10T12:30:00+03:00",
  "channel_mode": "auto",
  "metadata": { "queue": "sales", "wait_seconds": 12 }
}
```

- Оператор определяется по приоритету: явный `seller_id` → `operator_mapping`
  (добавочный → seller_id в настройках) → `default_seller_id`.
- Дедупликация по `(organization_id, external_call_id)` — повторный вебхук вернёт
  `duplicate: true` без создания дубля.
- `recorder.telephony_settings` хранит токен и дефолты.

### Поля звонка в БД

`recorder.recordings`: `source` (badge | manual | transcript | call_manual | call_webhook),
`call_direction`, `client_phone`, `operator_phone`, `external_call_id`, `call_metadata` (JSONB).

## Анализ звонков

### Исходы (outcome) для телефонии

Если запись — звонок (source=call_* или указан call_direction), общий анализ использует
телефонийный набор исходов вместо розничного:

| Исход | Значение |
|-------|----------|
| `purchase` | Заказ/заявка оформлены в звонке |
| `appointment` | Назначена встреча/запись/замер |
| `callback` | Договорились о повторном звонке |
| `deferred` | Клиент думает, без конкретного шага |
| `refusal` | Явный отказ |
| `transfer` | Звонок переведён |
| `non_target` | Нецелевой звонок/спам |
| `voicemail` | Автоответчик/недозвон |
| `unknown` | Не определён |

### Метрики динамики разговора

Считаются из таймкодов сегментов без LLM (`analytics-engine/app/dynamics.py`) и
сохраняются в `analytics.conversations`:

- `talk_ratio` — доля речи оператора от всего времени речи (ориентир 40–60%)
- `interruptions_count` — перебивания (пересечение таймкодов реплик ≥300мс)
- `longest_monologue_seconds` — самый длинный монолог оператора
- `silence_ratio` — доля тишины (паузы ≥1.5с) от длительности разговора

Отображаются в карточке разговора. Скоринг скриптов, возражения, апсейл/кросс-сейл и
комплаенс работают для звонков без изменений.

## Полнотекстовые скрипты (script_type = fulltext)

Для КЦ-сценариев, где скрипт — это подробный документ, а не набор этапов.

**Импорт:** Скрипты → Создать → «Из документа» → загрузка DOCX/PDF/RTF/TXT →
LLM разбивает документ на блоки (обязательные и ситуативные) → предпросмотр и правка →
сохранение. Эндпоинт: `POST /api/v1/scripts/templates/import-document`.

**Структура:** `scripts.script_templates.script_type` + `scripts.script_blocks`
(title, text, block_type, is_mandatory, block_order). Исходный текст хранится в
`full_text`, имя файла — в `source_document_name`.

**Скоринг:** для каждого блока LLM определяет статус:
- `spoken` (100) — произнесён близко к тексту,
- `paraphrased` (70) — донесён своими словами,
- `missed` (0) — блок **требовался** в разговоре, но не прозвучал (реальный пропуск),
- `not_applicable` — ситуация для блока не возникла (клиент не возражал/тему не поднимал).

Балл скрипта = среднее по блокам, которые реально требовались (статус ≠ `not_applicable`).
Это ключевое решение: ситуативные блоки (ответ на возражение по цене и т.п.) попадают в балл,
только если соответствующая ситуация возникла в разговоре, — иначе они не штрафуют оператора
и не портят тепловую карту. Обязательные блоки (`is_mandatory`) нужны всегда: для них
`not_applicable` не допускается (трактуется как `missed`). Если ни один блок не потребовался,
`script_score = NULL` (скрипт неприменим к этому разговору, в средний балл не входит).

Детализация пишется в `conversation_script_results.block_results` (JSONB) и отображается
в карточке разговора: статус каждого блока, цитата оператора, текст скрипта. Аналитика по
скрипту (раздел «Скрипты» → «Детально по блокам») агрегирует покрытие по блокам, исключая
`not_applicable` из знаменателя.

Назначения, версии и контекстные скрипты работают для fulltext так же, как для этапных.

## Настраиваемые типы возражений

Раньше 7 типов возражений (`price`, `quality`, `competitors`, `timing`, `trust`, `not_ready`,
`functionality`) были захардкожены. Теперь это справочник на уровне организации —
`scripts.objection_types` (CRUD: `/api/v1/scripts/objection-types`, UI: Скрипты → вкладка
«Типы возражений»). При первом обращении 7 стандартных типов сидируются лениво.

- Директор/админ/менеджер может добавить свои отраслевые типы с **примерами фраз** —
  примеры подставляются в промпт общего анализа и учат LLM ловить специфику
  (например, «страх боли» для стоматологии, «возражение по срокам замера» для застройщика).
- Стандартные типы нельзя удалить (исторические `analytics.objections.type` ссылаются на коды),
  но можно выключить или дополнить примерами.
- Воркер `analytics-engine` подтягивает активные типы организации и через
  `apply_objection_types()` подставляет коды в JSON-схему промпта и расшифровку в user-промпт.
  Неизвестный код от LLM не валит ответ (мягкая нормализация в воркере).

## Фильтры на странице разговоров (telephony)

- Направление: входящие / исходящие
- Источник: звонки (все), из АТС, вручную, загруженное аудио, транскрипты
- Параметры API: `GET /api/v1/dashboard/conversations?direction=&source=&client_phone=`
