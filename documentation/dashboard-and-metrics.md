# Дашборд и метрики

## Dashboard Service — Backend for Frontend

Dashboard Service — это специальный сервис-прослойка (BFF, Backend for Frontend). Его единственная задача — собирать данные из разных таблиц PostgreSQL, агрегировать их в удобный для фронтенда формат и отдавать быстро за счёт кэширования в Redis.

**Принцип работы:**
- Dashboard Service не создаёт данные — он только читает и агрегирует
- Все тяжёлые вычисления (агрегации, сортировки, группировки) выполняются на стороне БД
- Результаты кэшируются в Redis, чтобы повторные запросы возвращались за миллисекунды
- При появлении новых данных кэш автоматически инвалидируется

## Ключевые метрики платформы

### Скоринг скрипта (%)

Показывает, насколько полно продавец выполнил этапы скрипта продаж.

**Как считается:**
```
score = Σ (балл_этапа × вес_этапа) для всего разговора
```

Значение от 0 до 100. В дашборде отображается среднее по продавцу/магазину за выбранный период.

**Интерпретация:**
- 90–100 — отличная работа по скрипту
- 70–89 — хорошо, но есть точки роста
- 50–69 — значительные пропуски, нужна работа с продавцом
- <50 — скрипт не соблюдается, требуется срочное внимание

### Конверсия (%)

Доля разговоров с клиентами, завершившихся покупкой.

**Как считается:**
```
конверсия = COUNT(outcome = 'purchase') / COUNT(*) × 100
```

Считается за выбранный период (7 / 30 / 90 дней). Фильтруется по магазину или продавцу.

### Распределение возражений

Показывает, какие типы возражений встречаются чаще всего и насколько успешно они закрываются.

```sql
SELECT type, COUNT(*) as count, AVG(is_resolved::int) as resolution_rate
FROM objections
WHERE conversation_id IN (-- разговоры за период и магазин --)
GROUP BY type
ORDER BY count DESC
```

## Разделы дашборда

### Обзор (Overview)

Главный экран с общими метриками. Обновляется каждые 5 минут (TTL кэша).

**Данные:**
- Общее количество разговоров за период
- Средняя конверсия (%)
- Средний скоринг скрипта (%)
- Тренды метрик за выбранный период (по дням)
- Распределение исходов (donut chart): покупка / отложено / отказ по цене / конкурент
- Алерты: продавцы с низким скорингом, серии отказов

**Период:** выбирается пользователем — 7, 30 или 90 дней. По умолчанию 30 дней.

### Команда (Team)

**Рейтинг продавцов (Leaderboard):**
- Сортировка по конверсии
- Рядом: скоринг скрипта
- Визуальные медали для топ-3
- Кэш: 15 минут

**Сравнение магазинов:**
- Таблица: магазин, количество продавцов, средний скоринг, конверсия
- Позволяет сравнить эффективность разных точек продаж

**Профиль продавца:**
- Личные метрики: конверсия, скоринг
- Детализация по этапам скрипта — где слабые места
- Рекомендации (шаблонные тексты из `recommendation_text` по этапам скрипта)
- Последние разговоры

### Разговоры (Conversations)

Список всех разговоров с фильтрами:
- По магазину, продавцу, исходу, диапазону дат
- По диапазону скоринга (например, только разговоры <70%)

Для каждого разговора в таблице:
- Дата и время
- Имя продавца
- Тема разговора (какой товар)
- Длительность
- Скоринг (цветовая индикация)
- Исход (тег: покупка / отказ / отложено)

По клику — детальная карточка разговора (Drawer).

### Аналитика (Analytics)

**Вкладка «Возражения»:**
- Donut chart: распределение типов возражений
- Таблица техник закрытия: какие техники чаще всего применяются и насколько эффективны
- Bar chart: топ продавцов по количеству возражений и проценту закрытия

**Вкладка «Конверсия»:**
- Bar chart конверсии по магазинам
- Динамика конверсии по времени

## Агрегации и расчёты

### Конверсия за период

```sql
SELECT
  COUNT(*) FILTER (WHERE outcome = 'purchase') AS purchases,
  COUNT(*) AS total,
  ROUND(
    COUNT(*) FILTER (WHERE outcome = 'purchase') * 100.0 / COUNT(*), 1
  ) AS conversion_rate
FROM conversations
WHERE organization_id = $1
  AND store_id = $2
  AND recorded_at BETWEEN $3 AND $4
```

### Тренды по дням

```sql
SELECT
  DATE(recorded_at) AS day,
  COUNT(*) AS total_conversations,
  AVG(overall_score) AS avg_score,
  COUNT(*) FILTER (WHERE outcome = 'purchase') * 100.0 / COUNT(*) AS conversion
FROM conversations
WHERE organization_id = $1
  AND store_id = $2
  AND recorded_at >= NOW() - INTERVAL '30 days'
GROUP BY DATE(recorded_at)
ORDER BY day
```

### Рейтинг продавцов

```sql
SELECT
  s.id,
  s.first_name,
  s.last_name,
  COUNT(c.id) AS total_conversations,
  ROUND(AVG(c.overall_score), 1) AS avg_score,
  ROUND(
    COUNT(*) FILTER (WHERE c.outcome = 'purchase') * 100.0 / COUNT(c.id), 1
  ) AS conversion_rate
FROM admin_schema.sellers s
LEFT JOIN analytics.conversations c ON c.seller_id = s.id
  AND c.recorded_at BETWEEN $1 AND $2
WHERE s.store_id = $3
  AND s.organization_id = $4
GROUP BY s.id, s.first_name, s.last_name
ORDER BY conversion_rate DESC
```

## Кэширование

### Стратегия

Dashboard Service кэширует каждый тяжёлый запрос отдельно.

**Структура ключа:**
```
dashboard:{organization_id}:{store_id}:{period}:{endpoint}
```

Примеры:
```
dashboard:org-456:store-123:30:overview
dashboard:org-456:store-123:30:leaderboard
dashboard:org-456:all:90:store-comparison
```

**TTL по типам запросов:**

| Endpoint | TTL | Причина |
|----------|-----|---------|
| `/overview` | 5 минут | Часто меняется при активном потоке записей |
| `/overview/trends` | 5 минут | Аналогично |
| `/team/leaderboard` | 15 минут | Менее чувствителен к задержке |
| `/team/store-comparison` | 15 минут | Аналогично |
| `/objections/distribution` | 15 минут | Медленно меняется |

### Инвалидация кэша

Когда analytics-engine завершает анализ нового разговора, он публикует в `queue.cache.invalidate`:

```json
{ "organization_id": "uuid", "store_id": "uuid", "seller_id": "uuid" }
```

Dashboard-service получает это событие и удаляет из Redis все ключи, начинающиеся с `dashboard:{organization_id}:{store_id}:*`. При следующем запросе с фронтенда данные будут заново агрегированы и закэшированы.

## Алерты

Алерты — это автоматические предупреждения для менеджеров о проблемах в работе команды.

**Важно:** пороги алертов **настраиваются в разделе «Настройки»** (таблица `alert_settings`), они не хардкодятся в системе. Значения по умолчанию применяются только если настройки не заданы явно.

**Типы алертов:**

| Тип | Условие (настраиваемый порог) | Кому показывается |
|-----|-------------------------------|------------------|
| Низкий скоринг | Средний балл продавца за неделю ниже порога (по умолчанию 60) | director, admin, rop, manager |
| Серия отказов | Более N исходов `price_refusal` или `competitor` подряд (по умолчанию 3) | admin, rop, manager |

Алерты формируются при запросе `GET /api/v1/dashboard/overview/alerts` — они не хранятся отдельно, а вычисляются на лету из актуальных данных с учётом настроенных порогов.

## Производительность

**Целевые показатели:**
- API дашборда: ответ < 500 мс (с кэшем)
- Первая загрузка данных (cache miss): < 3 секунды
- Frontend First Contentful Paint: < 2 секунды
