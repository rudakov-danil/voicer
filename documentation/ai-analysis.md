# AI-анализ — логика работы

Analytics Engine — это сердце платформы. Он получает готовый транскрипт разговора (с уже определёнными ролями спикеров) и выполняет анализ в три этапа LLM-запросов, превращая текст в структурированные бизнес-метрики.

---

## Как запускается анализ

Анализ запускается автоматически — не через API, а через очередь сообщений. После того как transcription-service определил роли спикеров, он публикует в `queue.analyze` задание:

```json
{
  "recording_id": "uuid",
  "transcript_id": "uuid",
  "seller_id": "uuid",
  "store_id": "uuid",
  "organization_id": "uuid"
}
```

Воркер `analytics-engine` забирает задание и выполняет анализ в три этапа (скрининг контекстных скриптов → скоринг → общий анализ). При необходимости анализ можно запустить повторно через `POST /api/v1/analytics/reanalyze/{id}`.

**Если у продавца нет назначенных скриптов:** скоринг не выполняется (поля `overall_score` и `conversation_scores` остаются пустыми). Остальные виды анализа — возражения и исход — выполняются в штатном режиме.

---

## LLM-запросы на анализ

Анализ выполняется в **три этапа LLM-запросов**:

**Этап 1 — Скрининг контекстных скриптов** (параллельно, по одному запросу на каждый контекстный скрипт):
```
Определи, применим ли этот скрипт к данному разговору.
Описание контекста скрипта: {context_description}
Транскрипт: {transcript}
Ответь JSON: { "applicable": true|false, "reason": "краткое обоснование" }
```
Обязательные скрипты этот этап **пропускают** — они применяются всегда.

**Этап 2 — Скоринг применимых скриптов** (параллельно, для обязательных + прошедших скрининг):
```
Ты — эксперт по продажам. Оцени, насколько продавец соблюдал скрипт «{script_name}».
Этапы скрипта: {script_steps_with_weights}
Транскрипт: {transcript}
Верни JSON: { "step_scores": [...], "violations": [...] }
```

**Этап 3 — Общий анализ** (один запрос, параллельно с этапом 2):
```
Проанализируй разговор: определи исход и найди возражения клиента.
Транскрипт: {transcript}
Верни JSON: { outcome, outcome_confidence, topic, sentiment_avg, objections: [...] }
```

**Что передаётся:**
- Транскрипт содержит метки ролей (`[Продавец]` / `[Клиент]`) — результат диаризации
- Список скриптов: `GET /api/v1/scripts/for-seller?seller_id=uuid` — включает `is_mandatory` и `context_description`

## Три вида анализа

### 1. Скоринг по скриптам продаж

**Цель:** оценить, насколько полно продавец прошёл этапы каждого назначенного скрипта.

**Логика:**
1. Движок запрашивает у `scripts-service` **все скрипты продавца**: `GET /api/v1/scripts/for-seller?seller_id=uuid`
2. Для каждого скрипта — отдельный LLM-запрос, который оценивает каждый этап:
   - `detected` (true/false): был ли этот этап в разговоре
   - `score` (0–100): насколько хорошо выполнен
   - `evidence`: цитата из транскрипта
3. Балл по скрипту = взвешенная сумма оценок этапов
4. **Итоговый `overall_score`** = среднее по всем скриптам

**Примеры оценок для этапа "Выявление потребностей":**
- 100 — продавец задал несколько уточняющих вопросов, выяснил сценарий и бюджет
- 70 — спросил про бюджет, но не уточнил сценарий использования
- 30 — формально спросил «чем помочь», но реально потребности не выяснял
- 0 — этап полностью пропущен

**Что сохраняется:**
- В `conversations`: `overall_score` (среднее по всем скриптам)
- В `conversation_script_results`: по одной записи на каждый скрипт — `script_score`, нарушения
- В `conversation_scores`: детальный скоринг по каждому этапу каждого скрипта с цитатой

---

### 2. Классификация возражений

**Цель:** найти все возражения клиента, определить их тип и понять, закрыл ли продавец каждое из них.

**Типы возражений:**

| Тип | Пример фразы клиента |
|-----|---------------------|
| `price` | "Это слишком дорого", "У конкурентов дешевле" |
| `quality` | "Я не уверен в качестве", "Слышал плохие отзывы" |
| `competitors` | "В другом магазине видел лучше", "Есть более известный бренд" |
| `timing` | "Сейчас не время", "Подожду до зарплаты" |
| `trust` | "Я не знаю этот бренд", "Не слышал о вашем магазине" |
| `not_ready` | "Мне нужно подумать", "Приду позже" |
| `functionality` | "Не хватает такой-то функции", "Это не совсем то, что мне нужно" |

**Логика анализа:**
1. LLM находит в тексте все фрагменты, где клиент выражает сомнение или возражение
2. Классифицирует каждый по типу из списка выше
3. Определяет, ответил ли продавец на возражение и снял ли его (`is_resolved: true/false`)
4. Если снял — какой техникой (`resolution_technique`, например: "trade-in программа", "гарантия возврата", "сравнение с аналогами")
5. Каждое возражение привязывается к конкретному сегменту транскрипта (`transcript_segment_id`) — для подсветки в UI

**Что сохраняется:**
- В таблице `objections`: тип, статус закрытия, техника, цитата из текста, ссылка на сегмент

---

### 3. Определение исхода разговора

**Цель:** понять, чем завершился разговор.

**Возможные исходы:**

| Исход | Значение |
|-------|---------|
| `purchase` | Клиент купил |
| `deferred` | Отложил покупку (придёт позже) |
| `price_refusal` | Отказал из-за цены |
| `competitor` | Ушёл к конкуренту |
| `unknown` | Исход не удалось определить |

**Дополнительно:**
- LLM возвращает `outcome_confidence` (0.0–1.0) — насколько уверен в классификации
- Извлекается `topic` — название товара или услуги (например, "Samsung Galaxy S25", "кофемашина DeLonghi")
- Вычисляется `sentiment_avg` — средняя эмоциональная окраска разговора (-1 до +1)

**Что сохраняется:**
- В `conversations`: `outcome`, `outcome_confidence`, `topic`, `sentiment_avg`

## Рекомендации для продавца

После завершения анализа для каждого непройденного или слабо выполненного этапа скрипта формируется рекомендация.

**Логика:**
- Для этапов с хорошим score (≥ 80) — показывается похвала без рекомендаций
- Для этапов со средним score (50–79) — показывается шаблонная рекомендация: `recommendation_text` из поля `script_steps`
- Для этапов с низким score (< 50) или `detected = false` — показывается шаблонная рекомендация с пометкой «требует внимания»

**Сортировка:** этапы в блоке рекомендаций отсортированы по тяжести проблемы (от худшего к лучшему).

**В MVP рекомендации — шаблонные фразы**, заданные администратором при создании этапа скрипта. Генерация через LLM запланирована на v2.

## STT и диаризация

**Важно:** analytics-engine работает уже с готовым транскриптом, в котором роли спикеров определены. Эти два шага выполняются до AI-анализа:

1. **STT (Speech-to-Text):** Whisper self-hosted транскрибирует аудио в текст с таймкодами. Whisper не разделяет спикеров — он просто переводит речь в текст.

2. **Идентификация ролей:** отдельный LLM-запрос в `transcription-service` разбивает текст на реплики и определяет, где говорит продавец, а где клиент. Имя продавца передаётся как контекст (известно из `device_id` → `seller_id` → `full_name`).

Подробнее — в [data-pipeline.md](./data-pipeline.md) и [badge-and-segmentation.md](./badge-and-segmentation.md).

## Выбор LLM

Используются **локальные языковые модели** на собственном GPU-сервере. Данные не передаются ни в какие внешние API — полное соответствие 152-ФЗ.

| Этап | Инструмент | Описание |
|------|-----------|---------|
| **MVP** | **Ollama** | Простой запуск открытых моделей (Llama, Mistral, Qwen и др.), стандартный REST API |
| **Продакшн** | **vLLM** | Высокая пропускная способность, OpenAI-совместимый API, batching |

Переключение через переменную окружения `LLM_URL` (адрес GPU-сервера). Конкретная модель подбирается при разработке — ориентир: модель с хорошим знанием русского языка (например, Qwen2.5-72B или аналог).

## Качество анализа и ограничения

**Что влияет на точность:**
- Качество аудиозаписи (шумы, несколько говорящих одновременно снижают точность)
- Качество транскрибации Whisper (ошибки STT напрямую влияют на анализ)
- Длина контекста LLM — очень длинные разговоры, не вмещающиеся в контекстное окно модели, разбиваются на части и анализируются последовательно с агрегацией результатов
- Специфика скрипта — чем конкретнее описаны этапы, тем точнее скоринг

**Уверенность и пороги:**
- `outcome_confidence < 0.5` — исход маркируется как ненадёжный, в UI показывается предупреждение
- Возражения без явного текстового подтверждения не записываются

**Повторный анализ:**
- Можно перезапустить через `POST /api/v1/analytics/reanalyze/{id}` — например, после обновления скрипта или улучшения промптов
