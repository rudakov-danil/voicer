# Роли и управление доступом

VoiceIQ использует двухуровневую систему ролей: **внутренняя** (для команды VoiceIQ) и **клиентская** (для сотрудников компании-клиента внутри своей организации).

---

## Два приложения

| Приложение | URL | Кто использует |
|------------|-----|----------------|
| Клиентская платформа | `app.voiceiq.ru` | Сотрудники компаний-клиентов |
| Внутренняя административная панель | `admin.voiceiq.ru` | Команда VoiceIQ |

Оба приложения полностью разделены. Аутентификация, токены и базы пользователей — независимы.

---

## Мультитенантность

Каждая компания-клиент — это отдельная **организация** (`organization`). Все данные жёстко изолированы по `organization_id`:

- Пользователи видят только данные своей организации
- Магазины, продавцы, разговоры, скрипты — всё привязано к организации
- API на уровне middleware проверяет принадлежность запрашиваемых ресурсов к организации из JWT-токена
- Прямой доступ к данным другой организации невозможен даже при наличии валидного токена

---

## Клиентские роли (`app.voiceiq.ru`)

Четыре роли с разными уровнями доступа внутри организации:

### Директор (`director`)

Руководитель компании. Видит всё, но ничего не изменяет.

**Доступно:**
- Полный просмотр аналитики по всей организации (все магазины, все продавцы)
- Все разделы: Дашборд, Разговоры, Команда, Аналитика
- Просмотр скриптов (без редактирования)
- Просмотр настроек (без изменений)

**Недоступно:**
- Создание и редактирование скриптов
- Управление пользователями
- Изменение настроек

---

### Администратор (`admin`)

Технический администратор организации. Управляет структурой и пользователями.

**Доступно:**
- Управление пользователями системы (создание, редактирование, деактивация аккаунтов Director / ROP / Manager)
- Управление магазинами (добавление, редактирование)
- Управление устройствами (бейджи): регистрация через QR-код, привязка к продавцу
- Управление продавцами (профили физических сотрудников) по всей организации
- Настройки конфиденциальности, алертов (раздел Settings)
- Просмотр аналитики по всей организации
- Назначение РОПу подчинённых магазинов

**Недоступно:**
- Редактирование скриптов продаж (это задача менеджера)

---

### РОП — руководитель отдела продаж (`rop`)

Региональный менеджер, отвечающий за несколько магазинов.

**Особенность:** РОП может быть привязан к **нескольким магазинам** одновременно (many-to-many связь через таблицу `rop_store_assignments`).

**Доступно:**
- Просмотр аналитики по назначенным магазинам
- Просмотр разговоров и профилей продавцов в назначенных магазинах
- Просмотр рейтинга продавцов и сравнение магазинов
- Просмотр скриптов

**Недоступно:**
- Редактирование скриптов
- Управление пользователями
- Изменение настроек системы

---

### Менеджер (`manager`)

Руководитель конкретного магазина. Привязан к одному магазину (`store_id`).

**Несколько менеджеров на один магазин:** несколько пользователей с ролью `manager` могут одновременно быть привязаны к одному магазину.

**Доступно:**
- Полный просмотр аналитики своего магазина
- Просмотр разговоров и профилей продавцов своего магазина
- **Создание и редактирование скриптов продаж** (`scope = manager_level`)
- **Назначение скриптов продавцам** (своим продавцам — как обязательных, так и контекстных)
- **Управление продавцами своего магазина**: создание профиля, редактирование, деактивация (увольнение)
- **Привязка бейджа к продавцу**

**Недоступно:**
- Данные других магазинов
- Управление пользователями системы (аккаунты Director / Admin / ROP / Manager — это задача Admin)
- Системные настройки

## JWT-токен

При входе пользователь получает пару токенов:
- **Access token** — короткоживущий (15 минут), содержит claims
- **Refresh token** — долгоживущий (30 дней), хранится в базе в виде хеша

### Структура JWT payload

```json
{
  "sub": "user-uuid",
  "organization_id": "org-uuid",
  "role": "manager",
  "store_id": "store-uuid",
  "rop_stores": [],
  "iat": 1710000000,
  "exp": 1710000900,
  "type": "access"
}
```

**Поля:**
- `sub` — идентификатор пользователя
- `organization_id` — обязательно для изоляции данных между клиентами
- `role` — роль внутри организации (`director` / `admin` / `rop` / `manager`)
- `store_id` — для менеджера: его магазин; для director и admin: `null`; для rop: `null` (его магазины берутся из отдельной таблицы)
- `rop_stores` — список магазинов для РОПа; пустой для остальных ролей
- `type` — `"access"` для access token

### Хранение токенов на клиенте

- Access token: в памяти (JavaScript variable) — не в localStorage, не в cookie
- Refresh token: в httpOnly cookie

---

## Изоляция данных в API

Каждый запрос к API проходит через middleware, который:

1. Извлекает `organization_id` из JWT
2. Автоматически добавляет `WHERE organization_id = ?` к каждому запросу к БД
3. Для менеджера — дополнительно фильтрует по `store_id`
4. Для РОПа — фильтрует по списку магазинов из `rop_store_assignments`

Прямое указание `organization_id` в параметрах запроса игнорируется — всегда берётся из токена.

---

## Привязка РОПа к магазинам

РОП назначается на магазины через таблицу `rop_store_assignments`:

```
rop_store_assignments:
  - rop_user_id  (FK → users)
  - store_id     (FK → stores)
  - assigned_at  (timestamp)
```

Назначение выполняет администратор организации через раздел управления пользователями.

## Внутренние роли (`admin.voiceiq.ru`)

Внутренняя панель предназначена только для сотрудников VoiceIQ. На MVP — одна роль.

### Super Admin

Единственная роль в `admin.voiceiq.ru`. Полный доступ ко всем функциям внутренней панели.

**Возможности:**
- Просмотр всех организаций и их статистики
- Создание новых организаций
- Управление статусом организации (активна / заблокирована)
- Регистрация бейджей и привязка к организации
- Управление лицензиями / подписками (детали модели TBD)
- Просмотр технических метрик (очереди, ошибки обработки)

Подробнее — в [super-admin.md](./super-admin.md).

## Регистрация бейджей

Бейдж должен быть привязан к организации до начала работы. Два варианта:

**Вариант 1 — через VoiceIQ (Super Admin):**
1. VoiceIQ получает партию бейджей
2. Super Admin в `admin.voiceiq.ru` вводит серийные номера и привязывает их к организации
3. Клиент в `app.voiceiq.ru` видит доступные бейджи и назначает их продавцам

**Вариант 2 — самостоятельная регистрация клиентом:**
1. Администратор организации открывает `app.voiceiq.ru` → Устройства → Добавить
2. Сканирует QR-код на бейдже (или вводит серийный номер вручную)
3. Бейдж регистрируется в системе и привязывается к организации
4. Далее администратор назначает бейдж конкретному продавцу

---

## Регистрация новой организации (онбординг клиента)

В MVP публичной самостоятельной регистрации нет. Организации создаются **вручную Super Admin** через `admin.voiceiq.ru`:

1. Super Admin создаёт организацию: название, slug, email первого администратора
2. Автоматически создаются:
   - Запись организации в таблице `organizations`
   - Первый пользователь с ролью `admin` (email берётся из формы)
   - Базовые шаблоны скриптов «из коробки»
3. Admin получает доступ к системе (механизм передачи пароля при первом входе — TBD) и приступает к настройке: добавляет магазины, продавцов, бейджи

Super Admin назначает лицензию и при необходимости выдаёт триал-период.

> ⚠️ **В перспективе (v2):** планируется публичная форма самостоятельной регистрации с верификацией email на `app.voiceiq.ru`.

## Аутентификация — порядок работы

1. Пользователь вводит email + пароль → `POST /auth/login`
2. Сервер проверяет пароль (bcrypt), создаёт access + refresh токены
3. Access token возвращается в теле ответа, refresh token — в httpOnly cookie
4. Все последующие запросы содержат access token в заголовке `Authorization: Bearer ...`
5. При истечении access token (401) — Axios-интерцептор автоматически вызывает `POST /auth/refresh`
6. Если refresh token истёк или недействителен — редирект на страницу входа

При logout refresh token немедленно инвалидируется через Redis blacklist.

## Управление пользователями (только admin)

| Действие | Endpoint |
|----------|----------|
| Список пользователей организации | `GET /api/v1/auth/users` |
| Создание нового пользователя | `POST /api/v1/auth/users` |
| Изменение роли / деактивация | `PATCH /api/v1/auth/users/:id` |
| Назначение РОПу магазинов | `POST /api/v1/auth/users/:id/stores` |

При создании пользователя администратор указывает: email, полное имя, роль и магазин (для manager). Пароль устанавливается пользователем при первом входе.

> ⚠️ **Первый вход и установка пароля:** механизм не определён для MVP. Возможные варианты (будут уточнены): временный пароль от администратора, ссылка-приглашение на email, принудительная смена пароля при первом входе. Этот раздел будет обновлён после принятия решения.

Деактивированный пользователь (`is_active: false`) не может войти в систему, но его данные сохраняются.

## Защита UI

Компоненты и маршруты, требующие определённой роли, оборачиваются в `<RoleGuard>`:

```typescript
// Только менеджер видит редактор скриптов
<RoleGuard roles={['manager']}>
  <ScriptEditor />
</RoleGuard>

// Директор, Admin и РОП видят сравнение магазинов
<RoleGuard roles={['director', 'admin', 'rop']}>
  <StoreComparison />
</RoleGuard>
```

При попытке открыть недоступный URL — редирект на главную страницу.
