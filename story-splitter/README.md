# Story Splitter

Автономный модуль для проверки распознавания казахской речи на записях стендапа.
Пайплайн: **аудио → расшифровка с таймкодами → выделение историй → нарезка аудио → перевод**.

Итоговая выдача на каждую историю: **название — аудиофрагмент — расшифровка с таймкодами**
(казахский оригинал и русский перевод рядом).

## Почему так собрано

| Решение | Причина |
|---|---|
| Deepgram `nova-3`, `language=kk` | Единственная модель Deepgram с казахским. Работает только в batch-режиме — стриминг для `kk` недоступен, поэтому файл уходит целиком. |
| Границы историй — номера сегментов, а не секунды | Модель не может выдумать несуществующий таймкод: любой номер отображается в точное время реального сегмента ASR. |
| Нормализация в 16 кГц моно перед ASR | Убирает расхождение таймкодов на VBR-записях и экзотических кодеках. |
| Окна с перекрытием | Часовой стендап не влезает в один запрос к LLM. История на стыке окон видна целиком в следующем окне и не теряется. |
| SQLite + локальная папка | Модуль не трогает Postgres и MinIO основного стека — его можно удалить целиком одной командой. |
| `LLM_DISABLE_THINKING=true` | `qwen3.6` у Yandex — reasoning-модель. Без этого флага она тратит **весь** лимит токенов на «размышление» и возвращает пустой `content` (см. ниже). |

## Грабли: reasoning-модели съедают лимит токенов

`qwen3.6-35b-a3b` (и другие think-модели) сначала пишут рассуждение, и только потом ответ.
При `max_tokens=4096` на окне в 150 сегментов рассуждение занимало **все** 4096 токенов:

```
finish_reason : length
completion    : 4096
content       : 0 символов      <- ответа нет
reasoning     : 13809 символов  <- всё ушло сюда
```

Что перепробовано на реальных данных:

| Приём | Результат |
|---|---|
| `max_tokens=16000` | Работает, но 6996 токенов на вызов и ~21k символов рассуждения впустую |
| `/no_think` в system-промпте | Не действует — Yandex игнорирует |
| `reasoning_options: {mode: DISABLED}` | HTTP 400, параметр не поддерживается |
| `chat_template_kwargs: {enable_thinking: false}` | Работает: рассуждение исчезает, расход падает до ~400 токенов |
| **`reasoning_effort: "none"`** | **Работает и это идиома репозитория** (см. `transcription-service/app/diarization.py`) — выбран он, расход 342 токена |

Последнее и включено по умолчанию. Провайдеру, который такого параметра не знает,
запрос уйдёт повторно уже без него — откат срабатывает один раз и запоминается,
чтобы не платить за два запроса каждый раз.

Дополнительно: если ответ всё-таки обрывается по лимиту, из обрезанного JSON
вытаскиваются уцелевшие объекты (`salvage_objects`) — частичный результат лучше пустого.

## Запуск

```bash
cd story-splitter
cp .env.example .env     # заполнить ключи, можно взять из основного .env проекта
docker compose up -d --build
```

Интерфейс: http://localhost:8099

Проверить конфигурацию: `curl -s localhost:8099/api/health | python3 -m json.tool`

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DEEPGRAM_API_KEY` | — | Ключ Deepgram, обязателен |
| `DEEPGRAM_MODEL` | `nova-3` | Модель ASR |
| `ASR_LANGUAGE` | `kk` | Язык распознавания |
| `LLM_SERVER_URL` | Yandex Cloud | OpenAI-совместимый эндпоинт |
| `LLM_MODEL_NAME` | — | Идентификатор модели |
| `LLM_DISABLE_THINKING` | `true` | Отключает reasoning у think-моделей |
| `TRANSLATE_TO_RU` | `true` | Переводить расшифровку на русский |
| `STORY_MIN_SEC` | `20` | Короче этого порога фрагмент историей не считается |
| `SEGMENT_WINDOW_CHARS` | `12000` | Размер окна транскрипта на один запрос к LLM |

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/jobs` | Загрузить аудио (multipart `file`), запускает обработку |
| `GET` | `/api/jobs` | Список задач со статусами |
| `GET` | `/api/jobs/{id}` | Задача с историями и расшифровкой |
| `POST` | `/api/jobs/{id}/retry` | Перезапустить обработку. По умолчанию переиспользует сохранённую расшифровку; `?force_asr=true` — распознать заново |
| `DELETE` | `/api/jobs/{id}` | Удалить задачу вместе с файлами |
| `GET` | `/api/jobs/{id}/export` | Выгрузка в целевом формате (JSON) |
| `GET` | `/api/stories/{id}/audio` | Аудиофрагмент истории (mp3) |

Статусы задачи: `queued → transcribing → segmenting → cutting → translating → done`,
при ошибке — `failed` с текстом в поле `error`.

## Формат выгрузки

```json
{
  "source": "standup.mp3",
  "language": "kk",
  "stories": [{
    "title": "Название на казахском",
    "title_ru": "Название на русском",
    "audio": "01-nazvanie.mp3",
    "start": "02:14", "end": "05:41",
    "transcript": [
      {"time": "02:14", "start_sec": 134.2, "end_sec": 138.9,
       "text": "казахский текст", "text_ru": "перевод"}
    ]
  }]
}
```

## Структура

```
story-splitter/
├── docker-compose.yml       свой стек на порту 8099
├── backend/
│   ├── Dockerfile           python:3.12-slim + ffmpeg
│   └── app/
│       ├── config.py        настройки из окружения
│       ├── db.py            SQLite: задачи и истории
│       ├── audio.py         ffmpeg: длительность, нормализация, нарезка
│       ├── asr.py           Deepgram nova-3
│       ├── llm.py           OpenAI-совместимый клиент + разбор JSON
│       ├── segmenter.py     выделение историй и перевод
│       ├── pipeline.py      оркестрация этапов
│       └── main.py          HTTP API + отдача интерфейса
├── frontend/index.html      интерфейс без сборки
└── data/                    аудио, нарезка, база (в git не попадает)
```

## Ограничения

- Обработка идёт в фоновой задаче FastAPI, очереди нет: параллельные загрузки
  конкурируют за CPU контейнера. Для теста этого достаточно, для потока нужен воркер.
- Качество казахского у Deepgram стоит сверять с оригиналом — перевод на русский
  в интерфейсе как раз для этого и нужен.
